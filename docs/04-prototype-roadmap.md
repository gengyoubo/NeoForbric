# 原型路线与验收

以下是调查形成的路线，目标持续固定为 Minecraft 1.21.1，基础环境采用 Java 21，依据 [NeoForge 目标分支配置](https://github.com/neoforged/NeoForge/blob/a2d6402a3c1eec093aef7e7d10ac5145906c199e/gradle.properties)。当前已交付 [Java 启动 / 类加载夹具](prototype.md) 并通过其测试；下面各阶段的真实 Minecraft、注册、映射、Mixin 和原生态模组验收仍待完成。

## 1. 阶段 0：固定输入与契约

交付物：准确 Forbric 上游及继承范围、开发工具链与依赖版本锁定、统一 API 最小契约、支持状态定义。

固定游戏原始输入与映射、各原生对照环境、样本模组 JAR 哈希，以及转换器版本。调查提交快照只是研究证据，不是可直接运行的完整依赖组合；尤其 Fabric Loader 0.16.10 是静态样本，不应据此自动选为项目依赖。

验收条件：每个实验可以用同一组输入重复执行；契约明确初始化、注册窗口、线程和侧别；依赖缺失、重复 mod id、错误游戏版本在调用模组入口前给出可定位错误。

**补充前置验收：映射与 Mixin。** 按 [专项调查的验证矩阵](05-mapping-and-mixin.md) 先完成 M01–M04 的命名、refmap 和访问规则检查，再建立单一 Mixin 服务与 X01–X04 的注入 / 结构变化实验。映射文件可以读取、API 样例可以编译，都不能替代这一步。早期统一 API 的原生对照可并行推进，但原生态模组加载成功的结论依赖此闭环。

**第三轮调查补充。** 按 [06–16 专项](06-stage3-investigation.md) 将注册窗口、发现 / 依赖图、接口 ABI、Transformer 排序和最小 Audit 纳入前置契约。原型至少覆盖直接注册与 Deferred supplier 的可见性、世界动态定义与 Holder 身份、合法与不合法的变换顺序。NeoForge 构建属性与 FML 传递依赖声明存在版本差异，先取得实际解析 / 安装产物，再锁运行组合；见 [来源索引](stage3-sources.md)。

## 2. 阶段 1：用新 Common Mod 验证最小统一服务

先使用一个不依赖复杂注入的新样例模组：注册一个物品，监听服务器与世界 Tick，加载一份自定义 JSON，发送一组 C2S / S2C 消息。可先用三端原生适配样例对照契约，但最终还要迁入自主内核。

| 实验 | 可检查的结果 |
| --- | --- |
| 注册与解析 | 物品仅注册一次；重复 id、过早解析和冻结后注册有明确诊断 |
| 启动与侧别 | 客户端、单人世界和专用服务器的入口 / 线程轨迹正确；专用服务器不加载客户端类 |
| Tick 与世界 | 固定 200 个服务器 Tick 内记录到对应开始 / 结束；维度实例分别记账；启动失败另行判定 |
| 重载 | 连续成功重载两次，无重复 listener；损坏 JSON 被报告，新 API 的旧状态按契约保留 |
| 网络 | 两个方向均走实际 encode / decode；接收线程正确；错误方向、未知必需类型与版本不符按契约处理 |
| 重启 | 两次进单人世界、退出与重进不积累监听器或旧服务器状态 |

阶段 1 的结论只能写成“统一 API 的这组契约通过”，不能称为三端既有模组兼容。

## 3. 阶段 2：自主启动与第一种原生态入口

建议先用低复杂度 Fabric 原生态模组验证发现、元数据、映射和入口，再接入服务器 Tick / 世界生命周期 API 子集。这是工程顺序建议；如准确 Forbric 上游已有可复用启动内核，可以调整顺序。

交付物：无游戏类型依赖的引导侧、单一游戏类定义路径、模组依赖解析、转换清单、侧别隔离、完整加载报告。

启动所有权按 [18](18-bootstrap-and-classloading.md) 固定：从 JVM main、服务选择、G 创建到实际 define 都由内核拥有；先运行 B-01～B-06 的机制夹具，再接 B-09 / B-10 的游戏入口与原生态 Java 入口。模块视图、library 冲突、TCCL 和语言 provider 采用明确准入范围；尚未验证的语言不默认回退 Java。

验收条件：不启动另外两套完整加载器；同一测试 JAR 在原生 Fabric 与 NeoForbric 中比较入口、注册状态和行为轨迹；Mojang / intermediary / SRG 转换的已覆盖成员能正确链接；必要 Mixin 注入实际执行，错误注入目标可归因。

加入 [发现探针 S3-D](09-discovery-and-metadata.md)、[变换探针 S3-T](08-access-and-transformers.md) 与 [审计探针 S3-A](16-transform-audit.md) 的最小子集。若样本包含 MixinExtras，必须用 [S3-X](13-mixinextras.md) 验证其 operation / local 行为，不能用普通 Inject 的结果替代。

仅通过 `fabric.mod.json` 识别、进入标题界面或没有 `ClassNotFoundException`，都不足以宣告这一阶段完成。

## 4. 阶段 3：逐个接入 NeoForge 与 Forge

分别接入元数据与依赖、构造参数、模组事件总线、注册与 setup。每次只扩大一个明确 API 子集，先 NeoForge 再 Forge 是建议顺序，不代表后者可以仅替换包名。

三个生态共用内核的模组图和注册服务；保留原 API 类型或部分真实实现时，将其作为被动载体，明确生命周期所有者，避免原加载器再次启动。

验收条件：各用一个固定 JAR 的原生环境作为对照；注册发生在对应合法窗口；延迟工作完成后才越过阶段屏障；受支持的运行事件有正确结果与次数；未知必需功能标为不支持，不用吞异常换取启动成功。

分别运行 [注册 S3-R](07-registries.md) 与 [事件 S3-E](10-event-semantics.md) 探针，确认 priority、receiveCanceled、结果修改和 enqueueWork 屏障。首批 JAR 若要求网络，必须提前执行 [S3-N](12-network-protocol.md)，完整走 login→configuration→play；payload 注册成功不能代替握手。

## 5. 阶段 4：结构与复杂领域

在初始加载路径稳定后，扩大伤害 / 交互、capability / attachment、网络协议、渲染、动态内容与持久化覆盖。注册定义、Holder、必要 ABI 和握手框架此前已纳入；这一阶段增加复杂功能，而不是首次补这些基础契约。

每个领域先提交调用点与结果契约，再编写原生对照探针。优先用能区分不同实现的实验，例如“取消是否发生在扣耐久前”“复制实体后数据是否共享错误”“连接协商失败时是否仍允许进入世界”。避免只检查统一事件方法被调用。

数据生命周期按 [S3-P](11-data-lifecycle.md) 单独立项；客户端 [S3-C](14-client-rendering.md) 和资源 / datagen [S3-L](15-resources-and-datagen.md) 另行验收。服务端通过不外推到客户端；存档、复制与同步也不互相替代。

## 6. 阶段 5：混装与保存重载

先分别验证每个样本及其依赖，再把通过的样本同时放入统一实例，测试跨生态引用、监听器顺序、共享注册内容与网络。对照至少包含客户端、单人集成服务器和独立专用服务器。

验收需要覆盖新建世界、运行、实际保存、退出和重新读取，同步检查物品与实体状态。完整混装失败时，隔离后的子集通过必须单独报告；不能修改原样本集合后仍称原集合兼容。

[17](17-cross-ecosystem-interoperability.md) 的 I-01 / I-02 / I-09 / I-10 应提前在阶段 3 的首批混装夹具执行：Fabric 注册的 Item、三方传递的同一 Stack、共同命令树与权限结果必须可观察。阶段 5 再扩展 provider / attachment、世界配置、保存重载与 worldgen 的完整互操作；具体父类 ABI 验收独立于普通 API 验收。

## 7. 报告等级与诊断

| 等级 | 能说明什么 |
| --- | --- |
| 发现成功 | 元数据被解析，依赖候选已找到 |
| 加载成功 | 受支持的入口和初始化完成，无已知必要转换失败 |
| 进入世界 | 该场景可以启动并连接 |
| 行为通过 | 指定探针与原生基线一致 |
| 混装通过 | 固定样本全集共同运行并保存重载通过 |

每项结果记录游戏 / 运行时版本、输入哈希、物理 / 逻辑侧、线程、阶段、事件轨迹和可复现步骤。失败报告至少指明模组、缺失类型 / 方法或转换目标、原命名空间与期望阶段。

失败恢复采用 [18 的 severity / 提交点建议](18-bootstrap-and-classloading.md)：可选依赖或非必需 Mixin 不等于可热卸载。代码 / 类定义 / 注册状态已提交且无法证明回滚时停止实例；缩减模组集需要重建图，报告原集合与有效集合。

本轮没有可报告的兼容率；初始样本也不适合外推到全部模组。

## 8. 开始实现前仍需决定

| 问题 | 本轮建议 | 未确定的内容 |
| --- | --- | --- |
| Forbric 基线 | 先确认准确仓库及提交 | README 未给链接；本次候选当前是 26.2 |
| 第一目标 | 统一 API 与一个原生态模组逐步验证 | 是否更重视现有 JAR 混装，需要后续明确 |
| API 边界 | 独立统一服务；保留必要生态门面 | 各生态原 API 的第一批支持清单 |
| 游戏基底 | 固定原版输入与一份最终类定义 | 最小结构变更与必要保留行为 |
| 命名与工具链 | Mojang names 为统一方向，导入时显式转换 | 可共同工作的准确依赖版本与构建步骤 |
| 支持策略 | 必需语义缺失时停止并说明 | 可选功能的降级范围、标记与后续恢复方式 |

这些问题不妨碍本轮调查完成，但应在实现对应部分前形成决策记录。

17 / 18 补充后，通用领域调查结束。下一步交付可运行启动夹具与原生态三模组互操作证据；版本规则按目标 / 行为和探针追踪，仅围绕实现中暴露的具体失败继续研究。
